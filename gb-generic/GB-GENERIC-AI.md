# GB/GBC 범용 1배속: 안 맞는 롬을 AI 와 함께 고치기

ff-bgm1x 의 GB/GBC 범용 방식은 게임마다 따로 맞추지 않고, 게임 자신의 사운드 드라이버 코드를 에뮬레이터 안의 작은 CPU(그림자)로 실제 시간 박자에 맞춰 돌립니다.
처음 보는 게임에도 쓰도록 만든 방식이지만, 사운드 엔진을 고친 개조 롬이나 흔치 않은 방식으로 소리를 내는 게임은 어긋날 수 있습니다.
이 문서는 그런 롬을 가진 사람이 **자기 롬 + 이 문서의 프롬프트 + 에뮬레이터 소스**를 AI 에게 주고, AI 가 **에뮬레이터의 처리 방식** 또는 **롬** 을 고치게 하는 방법을 설명합니다.

- 1장: 사람용 안내 (준비물, 순서, 주의)
- 2장: 프롬프트 ㉮ 에뮬레이터 처리 방식 고치기
- 3장: 프롬프트 ㉯ 롬 고치기
- 3-1장: 프롬프트 ㉰ 그 롬 전용 처리를 에뮬레이터에 넣기 (㉮ 로 안 될 때)
- 4장: 진단표 (증상 → 볼 기록 → 원인 후보 → 일반 규칙으로 고친 예)
- 5장: 시험 도구 명령 모음
- 부록 A: 동작 구조
- 부록 B: 지금까지 고친 일반 규칙

---

## 1. 사람용 안내

### 언제 쓰나
- 배속 중 BGM 이 빨라지거나, 음이 빠지거나, 박자가 밀리거나, 한 채널만 들리는 등 원본과 다르게 들릴 때.
- 사운드 엔진을 고친 개조 롬은 어긋날 가능성이 큽니다.

### 준비물
1. **자기 롬 파일** (직접 가진 것). 롬은 AI 작업 폴더 안에서만 쓰고, 고친 롬이나 롬에서 뽑은 데이터를 남에게 나누지 마세요.
2. **에뮬레이터 소스**: ff-bgm1x 저장소의 GB 범용 방식 소스.
   - mGBA: `src/platform/qt/GbDriverGeneric.cpp/.h`, `GbShadowCpu.cpp/.h`, `GbNativeApuMgba.cpp/.h`, `GbDriverBgm.cpp/.h`, 코어 갈고리 `src/sm83/sm83.c`, `src/gb/memory.c`
   - VBA-M: `src/wx/ffbgm/gb_driver_generic.*`, `gb_shadow_cpu.*`, `gb_driver_bgm.*`, 코어 갈고리 `src/core/gb/gb.cpp`
   - Gambatte(libretro): `libgambatte/libretro/ffbgm/gb_driver_generic.*`, `gb_shadow_cpu.*`, 코어 갈고리 `libgambatte/src/cpu.cpp`, `interrupter.cpp`, `gambatte-memory.h`
   - 시험 도구: `src/tools/gb_generic_test.cpp`, `src/tools/compare_wav.py`, `src/tools/gb_regs_render.cpp`, 빌드 `src/scripts/build_gb_generic_test.sh`, 분석 스크립트 `work/porting-docs/gb-generic/tools/*.py`
3. 코드를 읽고 빌드·실행할 수 있는 AI 도구 (예: 터미널에서 명령을 실행하는 코딩 AI).

### 고르기: ㉮ 와 ㉯
| | ㉮ 에뮬레이터 처리 방식 고치기 | ㉯ 롬 고치기 |
|---|---|---|
| 고치는 곳 | 추적기·그림자 코드 (모든 게임에 적용) | 자기 롬 한 개 |
| 좋은 점 | 다른 게임도 함께 좋아질 수 있음 | 에뮬레이터를 다시 빌드하지 않아도 됨 |
| 조심할 점 | 다른 게임이 나빠지지 않는지 여러 롬으로 다시 재야 함 | 게임 동작이 바뀌지 않게 해야 함, 고친 롬은 나누지 않음 |
| 맞는 경우 | 드라이버를 찾는 규칙이 이 롬의 구조를 못 따라감 | 롬의 사운드 코드가 에뮬레이터 규칙으로 다루기 어려운 모양 |

먼저 ㉮ 로 원인을 찾게 하고, 에뮬레이터 규칙으로 풀기 어렵다는 결론이 나오면 ㉰(그 롬 엔진 전용 처리를 에뮬레이터에 넣기) 또는 ㉯ 를 쓰는 순서를 권합니다.

### 순서
1. AI 작업 폴더에 롬과 에뮬레이터 소스를 둡니다.
2. 2장 또는 3장의 프롬프트를 붙여 넣고, 롬 경로와 증상(어느 장면, 어떻게 다른지)을 적습니다.
3. AI 가 시험 도구로 원본과 그림자를 비교하고 고칩니다. 4장의 판단 기준을 넘는지 확인하게 합니다.
4. 고친 에뮬레이터를 빌드해 실제로 들어 봅니다.

## 2. 프롬프트 ㉮: 에뮬레이터 처리 방식 고치기

아래를 그대로 붙여 넣고, 끝의 `[ ]` 칸을 채우세요.

```text
너는 ff-bgm1x 의 GB/GBC 범용 1배속 BGM 코드를 고친다. 이 코드는 게임의 사운드 드라이버를 자체 SM83 해석기(그림자)로 실제 시간 박자에 돌려,
배속 중에도 BGM·효과음을 1배속으로 낸다. 어떤 롬에서 원본과 다르게 들린다. 원인을 찾아 에뮬레이터 쪽 일반 규칙으로 고쳐라.

지킬 규칙
1. 롬마다의 예외(특정 주소·뱅크·게임 판별)를 넣지 않는다. 고치는 것은 추적기·그림자·상태 넘김의 일반 규칙이다.
2. 추측하지 말고 기록으로 확인한다. 원인을 말할 때는 그 근거가 된 기록 줄이나 수치를 함께 보인다.
3. 고친 뒤에는 이 롬만이 아니라 가진 다른 GB 롬들도 다시 재서, 나빠진 것이 없는지 표로 보인다.
4. 롬과 롬에서 뽑은 데이터를 소스·주석·커밋·문서에 넣지 않는다. 게임 이름도 쓰지 않는다.
5. 고치는 안이 여럿이면 최소 3개를 보이고, 사용자가 고른 뒤 구현한다.

동작 구조 (자세히는 work/porting-docs/gb-generic/GB-GENERIC-AI.md 부록 A)
- 추적기(GbDriverTracer): 원본 CPU 의 명령·인터럽트·메모리 쓰기를 받아 호출 스택을 따라간다.
  갱신 루틴 = 인터럽트(또는 주 흐름) 안에서 사운드 레지스터 FF10~FF3F 쓰기를 모두 품는 함수.
  요청 함수 = 갱신 루틴 밖에서 드라이버 RAM 에 쓰는 코드를 품고 게임 RAM·화면을 건드리지 않는 가장 바깥 함수.
- 그림자(GbDriverShadow): 넘겨받은 요청 호출·RAM 쓰기를 같은 순서로 넣고, 갱신 루틴을 실제 시간 박자로 부른다.
  Pace 이벤트로 원본이 덜/더 부른 횟수만큼 박자를 늦추고 당기며, Mark 이벤트(원본이 갱신을 부른 곳)로 요청과 갱신의 순서를 맞춘다.
- 소리는 그 앱 코어의 GB 사운드 장치를 하나 더 만들어 낸다(GbNativeApu).

진단 순서
1. 시험 도구를 빌드한다: bash src/scripts/build_gb_generic_test.sh (PATH 에 MSYS2 ucrt64 bin).
2. 1배속과 4배속으로 돌린다: GB_REGLOG=1 gb_generic_test.exe <롬> <출력폴더> <초> <배속> "" 1
   필요하면 입력을 넣는다: 다섯째 인수 "프레임:키:길이,..." (키는 비트값: A=1 B=2 Select=4 Start=8 오른쪽=16 왼쪽=32 위=64 아래=128).
3. 로그(log.txt)에서 "update routine", "learned request", "update routine changed/added" 줄을 본다. 갱신 루틴을 못 찾았거나 엉뚱하게 바뀌었는지 먼저 본다.
4. 레지스터 순서 일치(regcmp.py), 시차(regoff.py, segoff.py), 소리 유사도(compare_wav.py), 소리 시차(lagcmp.py)를 잰다.
5. 4장 진단표로 원인 후보를 좁히고, GB_TRACE_WRITES·GB_TRACE_FROM/TO 로 그 구간의 호출 스택·사운드 쓰기를 찍어 확인한다.
6. 일반 규칙으로 고치고, 이 롬과 다른 롬들을 1·4배속 모두 다시 잰다.

판단 기준 (수치)
- 레지스터 순서 일치: 1배속 99% 이상, 4배속 95% 이상
- 레지스터 시차: 대부분 0 프레임
- 소리 유사도(compare_wav.py 전체 평균): 0.92~0.98. 원본이 소리 꺼짐 상태에서 직류만 내는 구간은 유사도가 0 으로 나오므로 따로 본다.

롬: [롬 경로]
증상: [어느 장면, 배속, 어떻게 다른지]
다른 시험 롬: [있으면 경로들]
```

## 3. 프롬프트 ㉯: 롬 고치기

```text
너는 사용자가 가진 GB/GBC 롬 하나를, ff-bgm1x 의 GB 범용 1배속 방식이 사운드 드라이버를 제대로 따라갈 수 있도록 고친다.
에뮬레이터 코드는 바꾸지 않는다. 게임의 동작(화면·입력·저장·진행)은 바뀌면 안 된다.

지킬 규칙
1. 고친 롬과 롬에서 뽑은 데이터는 작업 폴더 밖으로 내지 않는다. 결과는 사용자 롬에만 적용하는 패치(IPS/BPS) 와 설명으로 남긴다.
2. 추측하지 말고 기록으로 확인한다. 바꾸는 주소마다 원래 명령과 바꾼 명령, 바꾼 까닭을 적는다.
3. 고치는 안이 여럿이면 최소 3개를 보이고, 사용자가 고른 뒤 고친다.
4. 고친 뒤에는 원본 롬과 고친 롬을 같은 입력으로 돌려 게임 화면과 원본 쪽 소리가 같은지, 그림자 소리가 원본에 맞는지 잰다.

범용 방식이 잘 따라가는 드라이버의 모양
- 갱신 루틴이 VBlank·타이머 인터럽트(또는 주 흐름의 프레임 처리) 안에서 call 로 불리고 ret 으로 돌아온다.
- 갱신 루틴은 화면(VRAM·OAM), 저장 RAM, 사운드 밖 I/O 를 건드리지 않는다.
- 곡·효과음 요청은 함수 호출 하나로 이루어지고, 그 함수는 드라이버 RAM 과 사운드 레지스터만 쓴다.

어긋나는 모양의 예와 롬에서 고치는 방향
- 갱신 루틴 안에서 화면이나 게임 RAM 을 함께 처리함 → 그 처리를 갱신 루틴 앞이나 뒤의 별도 호출로 옮긴다.
- 갱신 루틴이 스택을 다른 곳으로 옮겨 쓰거나, 스스로 고치는 코드(RAM 에 복사해 실행)를 씀 → 롬 안의 같은 코드를 직접 부르게 바꾼다.
- 요청이 함수 호출 없이 여러 곳에서 드라이버 RAM 에 직접 씀 → 그 쓰기를 함수 하나로 모아 부르게 바꾼다.

진단 순서
1. 에뮬레이터 시험 도구로 원본 롬을 1배속으로 돌리고 로그의 "update routine", "learned request" 를 본다 (2장 진단 순서 1~4 와 같음).
2. 디스어셈블러로 갱신 루틴과 그 호출 경로, 요청 함수를 읽고 위의 어긋나는 모양 중 무엇인지 찾는다.
3. 고친 롬으로 다시 돌려 2장의 판단 기준을 넘는지 본다.

롬: [롬 경로]
증상: [어느 장면, 배속, 어떻게 다른지]
```

## 3-1. 프롬프트 ㉰: 그 롬 전용 처리를 에뮬레이터에 넣기

㉮ 로 일반 규칙을 찾지 못했을 때 씁니다. 아래를 그대로 붙여 넣고, 끝의 `[ ]` 칸을 채우세요.

```text
ff-bgm1x 의 GB/GBC 범용 1배속 BGM 이 이 롬에서 어긋난다. 아래 규칙으로 이 롬 전용 처리를 에뮬레이터에 넣어라.

1. 먼저 10분 동안 범용 규칙(GB-GENERIC-AI.md 2장)으로 고쳐 본다. 안 되면 원인과 근거를 보이고 전용 처리로 넘어간다.
2. 이 롬 엔진의 갱신 루틴·요청 함수 입구와 엔진 RAM 변수를 원본 CPU 기록으로 찾는다.
3. 그 값들은 롬 바이트 패턴(주소 자리는 와일드카드, 롬에서 한 곳에만 맞을 때만)으로 찾아 읽는다. 주소를 소스에 하드코딩하지 않는다.
4. 패턴이 맞으면 그 입구를 학습 대신 쓰고, 맞지 않으면 범용 학습 그대로 둔다.
5. 시험 도구와 TAS·버튼 입력으로 곡이 바뀌는 장면까지 두 코어에서 확인하고, 다른 롬이 나빠지지 않았는지 표로 보인다.
6. 게임 이름·롬 데이터·롬 시험 사실을 소스·주석·커밋·문서에 넣지 않는다. 안이 여럿이면 3개 이상 보이고 고르게 한다.

롬: [롬 경로]
증상: [어느 장면, 어떻게 다른지]
입력: [TAS 파일 또는 버튼 입력]
```

## 4. 진단표

| 증상 | 볼 기록 | 원인 후보 | 일반 규칙으로 고친 예 |
|---|---|---|---|
| 소리가 아예 안 남 | log.txt 에 "update routine" 줄 없음 | 갱신 루틴을 못 찾음 (사운드 쓰기가 인터럽트 처리 함수 자체에 있음, 스택을 옮긴 채 씀 등) | 인터럽트 처리 함수는 갱신 루틴으로 고르지 않음. 공통 경로가 인터럽트 처리 함수까지 줄면 사운드 쓰기 갈래별로 고름 |
| 한 채널만 들림, 곡이 끊김 | "update routine" 이 채널 하나를 맡는 함수 | 인터럽트마다 다른 채널 함수만 사운드를 씀 | 인터럽트별 호출 경로의 공통 앞부분으로 자르고, 화면·저장 RAM·사운드 밖 I/O 를 안 건드린 함수까지 위로 넓힘 (공통+순수 넓히기) |
| 처음엔 맞다가 엉뚱해짐 | "update routine changed to" | 게임 시작 직후 초기화 코드를 잘못 잡았다가 바꿈, 또는 바꾸지 말아야 할 것을 바꿈 | 확정 뒤 120번 연속 다른 후보일 때만 바꿈. 인터럽트 처리 함수로는 바꾸지 않음 |
| 효과음·곡 시작이 늦거나 빠짐 | "learned request" 목록, regoff.py 시차 | 요청 함수를 잘못 배움 (갱신 루틴 자신, 범용 복사·뱅크 전환 함수) | 갱신 루틴은 요청으로 배우지 않음. 그림자에서 정상으로 돌아오지 않거나 게임 RAM 을 두 번 건드린 함수는 버림 |
| 갱신 루틴이 여럿 붙음 | "update routine added" 가 많음 | 확정 뒤 한 번 지나간 경로까지 루틴으로 더함 | 이미 아는 루틴이나 배운 요청 함수를 지나는 갈래는 더하지 않음. 새 루틴은 20개 인터럽트에서 되풀이될 때만 |

| 엔진 입구를 못 봄 | 갱신 루틴이 뱅크 0 의 작은 함수 | 중계 함수(jp hl), 꼬리 호출(뱅크 전환 뒤 jp) | 함수 첫 명령의 중계를 따라가 실제 입구를 씀. 멀리 jp 하는 꼬리 호출을 기록해 넘겨받은 곳으로 바꿈 |
| 채널 3(파형) 이 안 울림 | 원본 쓰기에 NR30~34 시작 비트가 처음 한 번뿐 | 채널을 한 번 켜고 주파수만 바꾸는 드라이버인데, 상태를 넘길 때 시작 비트가 지워짐 | 상태 넘김(Init) 에서 파형 RAM 먼저, NR52 상태 비트로 울리던 채널은 시작 비트를 켜서 넣음 |

## 5. 시험 도구 명령 모음

시험 도구 소스는 이 폴더의 `test-tools/src/` 에, 분석 스크립트는 `tools/` 에 있습니다.
아래 경로(`src/...`, `work/...`)는 만든 사람의 작업 폴더 기준이므로, 에뮬레이터 소스(포크의 `gb-generic` 브랜치) 옆에 맞게 바꿔 쓰세요.

### 빌드
```bash
export PATH=/c/msys64/ucrt64/bin:$PATH
bash src/scripts/build_mgba.sh            # libmgba.a (한 번)
bash src/scripts/build_gb_generic_test.sh # work/build/tests/gb_generic_test.exe
```

### 실행
```bash
GB_REGLOG=1 work/build/tests/gb_generic_test.exe <롬> <출력폴더> <초> <배속> "<입력>" 1
```
- 인수: 롬, 출력 폴더, 초, 배속(1·4 등), 입력(`프레임:키:길이` 를 쉼표로), 마지막 1 은 GscPlayer 비교를 끔.
- 출력: `ref.wav`(원본 코어 소리, 1배속에서만), `gen.wav`(그림자 소리), `ref_regs.txt`·`gen_regs.txt`(프레임 레지스터 값), `ref_regs_t.txt`(원본 쓰기 시각), `log.txt`.

| 환경 변수 | 뜻 |
|---|---|
| `GB_REGLOG=1` | 원본·그림자의 사운드 레지스터 쓰기 기록 |
| `GB_TRACE_WRITES=1` + `GB_TRACE_FROM=<프레임>` `GB_TRACE_TO=<프레임>` | 그 구간의 사운드 쓰기마다 호출 스택, 프레임마다 갱신 호출 수·Pace 계산을 log.txt 에 |
| `GB_FRAMELEN=1` | 원본 프레임 길이가 보통(70224 사이클)과 다른 프레임 |
| `GB_SAV=<경로>` | 저장 파일을 넣고 시작 |
| `GB_CH1X=<16진 비트>` | 1배속으로 낼 채널 (비트 0~3 = 채널 1~4) |
| `GB_REF_MUTE=<16진 비트>` | 원본 녹음에서 끌 채널 |
| `GB_SELF_SYNTH=1` | 그림자 소리를 앱 코어 사운드 장치 대신 자체 합성기로 |
| `GB_APUCMP=1` | 원본 쓰기를 같은 시각에 받는 재현 장치와 원본 장치의 상태를 프레임마다 비교 |

### 분석
```bash
python src/tools/compare_wav.py ref.wav gen.wav            # 초별·전체 스펙트럼 유사도
python work/porting-docs/gb-generic/tools/regcmp.py ref_regs.txt gen_regs.txt   # 레지스터 순서 일치율
python work/porting-docs/gb-generic/tools/regoff.py ref_regs.txt gen_regs.txt   # 시차 분포
python work/porting-docs/gb-generic/tools/segoff.py ref_regs.txt gen_regs.txt   # 시차가 바뀌는 프레임
python work/porting-docs/gb-generic/tools/lagcmp.py ref.wav gen.wav             # 초별 소리 시차
gb_regs_render <regs.txt> <out.wav> <프레임 수> [mgba <기종>]   # 쓰기 기록만으로 소리 만들기 (합성기 문제와 드라이버 문제 가르기)
```
- Python 스크립트는 numpy·scipy 가 필요합니다 (MSYS2 의 python 이 아니라 numpy 가 깔린 python 으로).

## 부록 A. 동작 구조

1. **갈고리**: 코어의 CPU 명령 가져오기·인터럽트·메모리 쓰기에서 추적기를 부릅니다.
2. **추적기(원본 쪽, 에뮬레이션 스레드)**
   - call/rst/인터럽트와 ret 을 따라 호출 스택을 만들고, 레벨(주 흐름·인터럽트)마다 사운드 쓰기를 품은 경로를 모읍니다.
   - **갱신 루틴 찾기**: 인터럽트마다 사운드 쓰기 경로의 공통 부분을 투표(3번)로 확정하고, 화면·저장 RAM·사운드 밖 I/O 를 안 건드린 범위에서 위로 넓힙니다. 인터럽트 안에서 못 찾으면 주 흐름에서 같은 경로를 20프레임(70% 이상) 보면 확정합니다. 갱신 루틴이 여럿이면 원본이 부르는 순서대로 모두 둡니다.
   - **드라이버 RAM 지도**: 그림자가 갱신 루틴을 돌리며 쓰기 전에 읽는 RAM.
   - **요청 함수 배우기**: 갱신 루틴 밖에서 드라이버 RAM 을 쓰는 코드를 품고 게임 RAM 은 건드리지 않는 가장 바깥 함수. 다음부터는 그 함수의 호출(레지스터·롬 뱅크·RAM 사본)을 그림자에 넘깁니다.
   - 갱신 루틴 밖의 RAM 쓰기는 프레임마다 묶어(WriteBatch) 넘깁니다.
   - 프레임 끝마다 Pace(원본이 실제 시간에 맞춰 불렀어야 할 횟수 - 실제 횟수)를, 원본이 갱신을 부를 때마다 Mark 를 넘깁니다. 타이머 인터럽트 드라이버는 TMA·TAC 로 간격을 압니다.
3. **그림자(오디오 스레드 또는 녹화)**
   - 처음과 갱신 루틴이 바뀔 때 Init 으로 원본 RAM·사운드 레지스터 상태를 받습니다 (파형 RAM 먼저, 울리던 채널은 시작 비트 켬).
   - 박자마다: 받은 이벤트 중 마지막 Mark 앞의 것을 넣고 → 갱신 루틴(들)을 부르고 → 나머지를 넣습니다. 요청 호출은 정상으로 돌아올 때만 반영합니다.
   - 박자 간격은 프레임당 호출 수(정수 또는 1/k) 또는 타이머 간격이며, Pace 만큼 늦추거나 당깁니다.
   - 소리는 앱 코어의 GB 사운드 장치를 하나 더 만들어 냅니다 (mGBA: GBAudio). 원본 코어에서는 1배속으로 낼 채널을 끕니다.
